A compact SwiftUI observability app built with Firebase Crashlytics, dependency injection, and Swift Testing.

This showcase is designed as a focused reference project: the UI stays simple, Firebase remains isolated from presentation code, and the app keeps running with a local console fallback when Firebase is not configured.

- **iOS 26.0+**
- **Swift 6.0+**
- **Xcode 26.2+**

## Features

### Diagnostic Flow

- Record a sample event with logs, custom keys, and a user identifier
- Record a non-fatal error with contextual information
- Trigger an intentional crash after a confirmation dialog
- Restrict intentional crashes to `Debug` builds
- Show the latest diagnostic action in the interface

### Observability and Testing

- Firebase Crashlytics isolated behind `ObservabilityService`
- Console fallback when Firebase is not configured
- Dependency injection through `AppContainer`
- Automatic dSYM upload after each build for readable crash reports
- Swift Testing coverage for diagnostic events, errors, and the test-crash confirmation flow

## Architecture

```text
CrashlyticsShowcase
├── App
│   ├── AppContainer
│   └── FirebaseAppDelegate
├── Presentation
│   ├── DiagnosticsView
│   ├── DiagnosticsViewModel
│   └── FirebaseStatusSection
├── Domain
│   ├── ObservabilityService
│   ├── CrashTrigger
│   └── DiagnosticError
└── Data
    ├── FirebaseCrashlyticsService
    ├── ConsoleObservabilityService
    └── DebugCrashTrigger
```

### Main Flow

```text
Diagnostics screen
-> Sample event or non-fatal error
-> ObservabilityService
-> Firebase Crashlytics or Xcode console fallback
```

## Technical Decisions

- `ObservabilityService` is the only observability dependency visible to the presentation layer.
- `FirebaseCrashlyticsService` is the only type that imports the Firebase Crashlytics SDK.
- `DiagnosticsViewModel` uses `@Observable` and `@MainActor` for predictable SwiftUI state updates.
- `CrashTrigger` keeps the intentional crash separate and testable without terminating tests.
- The app calls `FirebaseApp.configure()` only when `GoogleService-Info.plist` is present in the bundle.
- The official Crashlytics build script uploads dSYMs after each build, so future crash reports include readable stack traces.
- Analytics, Remote Config, and A/B testing remain out of scope.

## Setup

1. Open `CrashlyticsShowcase.xcodeproj` in Xcode 26.2 or later.
2. Wait for Swift Package Manager to resolve `firebase-ios-sdk`.
3. Select the `CrashlyticsShowcase` scheme.
4. Run the `CrashlyticsShowcase` target.

The app works without Firebase configuration: diagnostic events are printed in the Xcode console. Configure Firebase to send reports to Crashlytics.

## Configuration

### Firebase Crashlytics

1. Create or select a project in the [Firebase Console](https://console.firebase.google.com/).
2. Add an iOS app with the same Bundle ID used by this project.
3. Enable Crashlytics and download `GoogleService-Info.plist`.
4. Add the file to the **CrashlyticsShowcase** target in Xcode.
5. Verify that it appears under `Build Phases` > `Copy Bundle Resources`.
6. Run the app again. The Firebase section should show that Crashlytics is configured.

`GoogleService-Info.plist` is included in `.gitignore`; if it was already added to Git, remove it from the index before committing. Avoid committing environment-specific configuration files to a shared repository.

### Validate a Crash Report

1. Run a `Debug` build with `GoogleService-Info.plist` configured.
2. Tap **Record sample event** and **Record non-fatal error**.
3. Tap **Trigger test crash** and confirm. The app closes intentionally.
4. Open the app again so the SDK can send the pending report.
5. Check the Crashlytics dashboard in Firebase. The first report can take a few minutes.

The test-crash action does not run in `Release`. The project uploads dSYMs after each build, so crashes generated by future builds can be symbolicated by Crashlytics.

## Tests

From the terminal:

```sh
xcodebuild test \
  -project CrashlyticsShowcase.xcodeproj \
  -scheme CrashlyticsShowcase \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=26.2'
```

The tests verify custom keys, logs, the user identifier, error context, user-facing status messages, and the Debug crash-confirmation flow.
